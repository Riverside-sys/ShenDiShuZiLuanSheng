# 所在部门介绍：TikTok Web 稳定性团队

## 一、部门定位

我实习所在的部门是 **TikTok Web 稳定性团队**。团队主要从预防、发现和治理等维度，为 TikTok Web 前端业务提供稳定性保障，并对核心服务的稳定性建设和用户体验兜底负责。

团队关注的最终结果不是建设了多少个平台或规则，而是两个核心问题：

- 能否减少用户可感知的严重线上故障；
- 故障发生后，能否更快完成发现、定位、止损和恢复。

因此，团队以用户可感知 Fatal 数量和 MTTR（平均恢复时间）作为主要结果指标，并持续提升监控覆盖率、报警召回率、报警准确率、归因效率和容灾覆盖率。

## 二、核心能力体系

团队围绕一次线上故障的完整生命周期，建设了“报警—归因—止损—知识库”四类核心能力。

### 1. 报警：更快发现问题

通过服务端可用性、页面崩溃、白屏、流量下跌和业务 SLI 等监控发现异常，同时建设统一报警管理能力，对报警进行分级、降噪、聚合、归因和分发。

这一阶段主要关注：监控是否覆盖核心业务、问题能否被及时召回，以及报警本身是否足够准确。

### 2. 归因：更快定位根因

将报警与发布变更、实验、流量变化、上下游依赖和实例状态等信息关联，帮助值班人员判断故障原因，缩短人工排查时间。

团队也在推动归因能力从“报警发生后的被动分析”向“变更期间主动检测风险”演进。

### 3. 止损：控制故障影响

针对不同故障层级建设降级、限流、切流和容灾能力，包括 CDN、动态域名、机房、服务、实例、网关等链路，使业务在局部故障发生时能够快速恢复或降级运行。

### 4. 知识库：沉淀治理经验

将历史事故、根因模式、处置过程和容灾预案结构化沉淀，使个人排障经验转化为可检索、可复用、可进一步自动化的组织能力。

## 三、团队的工作特点

### 1. 数据驱动

团队使用 Fatal、MTTR、召回率、准确率和容灾覆盖率等指标衡量建设效果，避免只统计平台功能数量而忽略实际稳定性收益。

### 2. 平台化治理

稳定性问题通常涉及多个服务、地区和系统。团队倾向于将重复治理过程沉淀为平台、算子、脚本或标准流程，提高覆盖范围和长期维护效率。

### 3. 跨团队协作

团队会与 TikTok Web 各业务团队合作，支持线上问题排查、监控加强、多机房部署、调度接入和容灾建设。稳定性团队提供基础能力和治理标准，业务团队提供业务上下文并共同完成风险治理。

### 4. 自动化与智能化

团队正在推动稳定性建设从人工排查和被动响应，逐步演进为自动巡检、自动归因、智能 OnCall 和归因驱动止损。AI Agent 可以在其中承担信息汇总、跨系统编排、治理状态推进和处置建议生成等工作，但高风险业务判断仍需要人工门禁和确定性规则保障。

## 四、我的工作与部门目标的关系

我的实习工作主要围绕“发现风险、治理问题、沉淀平台能力”展开：

1. **ByteFaaS 核心服务等级治理**：推动核心服务完成等级和报警准入条件对齐，并开发每日巡检算子，防止配置回退；
2. **报警策略平台建设**：参与报警策略的前后端开发，帮助核心资产提高报警覆盖和闭环能力，同时降低非核心报警噪音；
3. **线上问题台账平台化**：统一 Radar、Fatal 和人工未召回数据，建设 Platform/Flinx 管理页面，并设计 Aime Human-in-the-loop Agent 工作流和 `fatal-governance` 示例 Skill。

这三项工作分别对应团队能力体系中的风险预防与巡检、报警治理、事故知识沉淀和智能化流程建设。

## 六、面试展开关键词

面试官继续追问时，可以从以下方向展开：

- 如何通过监控覆盖率、召回率和准确率评价报警体系；
- 为什么稳定性治理需要区分报警事实、事故事实和人工治理字段；
- 如何通过幂等、事务、状态机和人工门禁控制自动化风险；
- 如何把一次性专项治理沉淀为巡检算子或平台能力；
- Agent 在稳定性场景中适合负责什么，以及哪些判断不应该交给大模型。
