# 实习产出总结（一）：ByteFaaS 核心服务等级治理、报警自动化与持续巡检

## 一、项目概述

### 1. 背景

早期部分 FaaS 函数服务在创建时统一申请为 P2 等级，但随着业务发展，其中一批服务已经进入 TikTok Web 核心链路。ByteFaaS 在资源紧张时会优先保障 P0/P1 服务，并可能延缓甚至中断 P2/P3 服务的扩容。因此，核心链路继续维持 P2 等级，会带来扩容排队、延迟上升和错误率抬升等稳定性风险。

项目首先盘点了 24 个核心 PSM 的资产等级和各区域实际服务等级，确认其中 19 个 PSM 尚未完成等级对齐，需要升级至 P0/P1。等级升级前还必须满足**高优服务准入条件**，包括：

- 核心 CPU、内存和异常退出报警配置为 Critical；
- Critical 报警通过 Phone、Lark 通知 Oncall，并接入 Avocado webhook；
- 服务具备 IPv6 Only 运行能力；
- 完成相应服务账号权限和升级工单流程。

这些准入条件涉及各 PSM 在 i18n、US-TTP、EU-TTP 三个区域的服务管理操作，执行前必须先取得对应 PSM 的服务权限。由于治理范围覆盖 24 个核心 PSM，若由个人账号逐服务、逐区域申请和配置，不仅操作量大，也不利于后续复用和权限交接。因此，我将部门服务账号作为统一的自动化执行身份，先批量申请三个区域的相关服务权限，再使用服务账号 JWT 调用治理脚本批量完成准入条件配置。

### 2. 工作目标

我的目标不是单次手工修改若干报警，而是建立一套可重复执行、可校验、可追踪的治理方法，完成“PSM 盘点 → 服务账号权限准备 → 报警配置 → 准入检查 → 等级升级 → 每日巡检 → 问题回收”的闭环，并为后续平台化治理提供可复用能力。

## 二、我的主要工作

### 1. 完成核心服务盘点与分层

我梳理了 24 个核心 PSM 在 i18n、US-TTP、EU-TTP 三个区域的当前等级，并与服务资产等级进行比对，识别出 19 个未对齐 PSM。根据资产等级和链路重要性确定 P0/P1 目标等级，为报警治理和后续提单提供统一输入。

这一步将原本分散的服务信息转化为结构化治理清单，明确了“哪些服务需要升级、升级到什么等级、各区域当前状态如何”。

### 2. 批量申请跨区域服务权限，打通自动化执行链路

高优服务准入配置并不是拿到 PSM 清单后即可直接执行。报警规则和相关服务配置分别属于各 PSM 在 i18n、US-TTP、EU-TTP 区域的管理资源，调用接口的身份必须具备对应服务权限。权限缺失会直接导致脚本无法查询或修改目标 PSM，因此，权限准备是批量治理能够落地的关键前置工作。

针对 24 个核心 PSM、3 个区域的治理范围，我采用部门服务账号统一承载自动化权限，并完成了以下工作：

1. 根据核心 PSM 清单整理需要申请权限的服务和区域范围；
2. 以部门服务账号为主体，批量申请各 PSM 在三个区域的相关服务操作权限；
3. 权限开通后，按区域获取服务账号 JWT，并在本地按区域隔离保存；
4. 将服务账号 JWT 注入 `fac` 脚本，由脚本以统一身份调用 Argos/ByteFaaS 接口；
5. 通过脚本批量查询、修改并启用核心报警，完成服务等级升级所需的准入条件配置。

相比依赖个人账号，这一方案将“人员身份”与“治理任务”解耦：权限集中在部门服务账号上，既支持跨 PSM、跨区域批量执行，也降低了实习结束或人员变更后自动化能力失效的风险，为后续周期性治理和平台化接管保留了稳定的执行身份。

### 3. 开发 ByteFaaS Alarm CLI

我开发了本地命令行工具 `fac`，将升级前的报警准备过程自动化。工具采用 Python 3.10+ 标准库实现，无额外第三方依赖，可独立于主仓库的 Go 构建和依赖体系运行。

工具的核心流程包括：

1. 读取接近 MaC 配置习惯的 XML 文件，解析 PSM、目标区域和报警阈值；
2. 分区域调用 Argos/ByteFaaS 接口，分页查询每个 PSM 的 prod 报警规则；
3. 自动识别并分类 CPU、内存和异常退出三类核心报警；
4. 根据全局默认值或服务级覆盖值生成 patch 计划；
5. 将目标报警更新为 Critical，配置 Phone、Lark 和对应区域的 Avocado webhook；
6. patch 成功后继续调用状态接口，确保报警处于启用状态；
7. 输出 UID 查询结果、patch 结果和本次执行汇总，支持问题追踪与失败重跑。

工具为 i18n、US-TTP、EU-TTP 分别维护区域配置和认证信息，能够按区域独立执行，降低跨区域批量操作的风险。

### 4. 开发 FaaS 服务等级每日巡检算子

在完成存量核心服务的等级升级后，我进一步开发了 `faas_level_check` 稳定性健康度指标算子，并接入 `reliability-health-operator` 的统一指标注册与调度框架，用于每天检测核心服务的 ByteFaaS 服务等级是否持续与资产等级对齐。这项工作将治理模式从“一次性整改”扩展为“存量整改 + 增量发现 + 配置防回退”。

算子的核心流程包括：

1. 从 Goofy Node FaaS 应用中提取 `faasCustomPsm` 及部署 Region，仅对适用的 FaaS 服务执行检查；
2. 从稳定性平台拉取 P0/P1 核心 PSM 资产清单和目标资产等级；
3. 将实际部署 Region 归并到 I18N、US-TTP、EU-TTP 三类目标区域，并通过 Keel 服务中心查询各区域当前 FaaS 服务等级；
4. 按 PSM 和 Region 对实际等级与资产等级进行比对，输出 `pass`、`fail`、`skip` 三态结果及 100、0、-1 的健康度分数；
5. 对确定存在等级缺失或不对齐的核心服务生成结构化 Issue，展示 PSM、资产等级、区域、当前等级和失败原因，并给出对应修复入口；
6. 在项目维度聚合各 PSM 结果，便于稳定性平台统一展示和后续问题跟进。

为减少误报和对下游接口的压力，我还补充了核心资产清单缓存、请求串行化与 1 QPS 限流、失败重试、区域映射和异常降级机制。只有查询成功且能够确定等级不合格时才创建 Issue；接口请求失败或区域无法识别时标记为 `skip` 并保留诊断信息，不将“无法判断”误判为“不合格”。

### 5. 建立安全、幂等的执行机制

由于非 dry-run 操作会真实修改线上报警，我在工具中加入了多层保护：

- `validate` 预检 XML、区域、阈值、webhook 和认证文件；
- 默认先使用 dry-run 生成计划，确认无误后再执行真实 patch；
- JWT 按区域存放在本地 `auth/` 目录并由 Git 忽略，避免凭据进入命令历史或代码仓库；
- 支持内部 CA，也提供仅限临时验证的 `--ssl-insecure` 开关；
- 网络请求带超时和最多 3 次重试，降低瞬时网络问题对批量任务的影响；
- 通过 `alarm_ready_psms.json` 记录已完成的 `PSM × 区域`，重复执行时自动跳过；
- 支持 `--rerun-ready` 强制重跑，且失败不会删除历史成功记录；
- 单个 PSM 失败时写入 `skipped_failed` 并继续处理其他服务，避免批量任务被单点问题阻断；
- 缺少某类报警时记录 warning，保留人工核查入口。

这些设计使脚本具备可预演、可中断恢复、可重复执行和可审计的工程属性，而不是一次性脚本。

### 6. 明确报警治理与工单升级的职责边界

在方案演进中，我将报警准备与升级工单解耦：当前 `fac` 专注于报警查询、分类、配置和就绪状态汇总，不直接提交或审批 ByteFaaS 工单；工单创建、人工 gate、next 确认和结果回收由外部平台或后续 Flinx 修复算子承接。

这一拆分形成了“健康度算子每日扫描 → fe_alarm 治理报警 → Flinx 修复升级 → 算子持续复检”的长期架构，减少不同环节之间的耦合，也便于独立重试、审计和扩展。其中，`faas_level_check` 已落地扫描发现和持续复检能力，为后续自动修复链路提供稳定的问题输入。

## 四、运行验证

### 1. 小规模验证

我先使用 3 条测试记录进行 dry-run，其中 1 条服务已经满足条件，工具正确识别出 2 条待执行记录，输出结果为 `todo=2、validated=2、manual_review=0`。真实执行后，两条待处理记录均完成报警准备，结果为 `ready=2、validated=0、manual_review=0`。

### 2. 平台结果核验

在 ByteFaaS/Argos 平台侧，我对实际修改结果进行了复核。以测试服务为例，CPU、内存和异常退出报警分别按 80、99、0.4 的阈值配置为 Critical，并处于启用状态，说明脚本不仅生成了请求计划，也实际完成了报警配置和状态开启。

### 3. 工单链路验证

早期原型还对升级工单进行了 dry-run：2 个 PSM 覆盖 3 个区域，共生成 6 个提单计划，并在发送前停止。该结果验证了请求参数、区域 workflow 配置和批量计划生成链路，但不计作真实工单提交结果。后续实现将工单职责从报警工具中拆出，由专门的修复流程承接。

### 4. 批量运行沉淀

当前脚本汇总文件累计记录 51 条 `PSM × 区域` ready 结果，覆盖 20 个去重 PSM，其中 i18n 15 条、US-TTP 20 条、EU-TTP 16 条；最近一次汇总无失败项、无人工复核项。该数据用于证明工具的实际批量运行能力，其统计口径与项目总体的 24 个核心 PSM 不同。

### 5. 每日巡检能力落地

`faas_level_check` 已完成指标处理器开发并注册到健康度算子的统一入口，可由平台按日触发。算子覆盖“FaaS 项目识别、PSM/Region 解析、核心资产筛选、Keel 等级查询、三态判定、项目级聚合和 Issue 生成”的完整链路，使新增核心服务或后续配置漂移能够被持续发现，而不再依赖人工定期复查。

## 六、产出价值

### 1. 稳定性价值

将核心链路服务等级由历史 P2 配置对齐到 P0/P1，使其在资源紧张和突发流量场景下获得与业务重要性一致的调度保障，降低扩容受阻造成的延迟和错误风险。同时通过每日巡检及时识别新增服务遗漏和配置回退，避免治理成果随时间衰减。

### 2. 效率价值

通过部门服务账号批量申请 24 个核心 PSM 在 3 个区域的相关权限，避免个人逐服务、逐区域申请和操作；在权限打通后，将跨区域报警查询、分类、配置和启用流程自动化，并通过 XML 批量输入和 JSON 结果沉淀，使新增服务可复用同一流程。巡检算子进一步替代人工定期盘点，将问题发现从临时专项检查转化为每日自动检测。

### 3. 工程价值

通过部门服务账号统一承载自动化权限，避免治理能力依赖个人身份，提高了长期可维护性和交接可靠性；通过 dry-run、预检、幂等记录、失败隔离和可重跑机制，将高风险线上批量操作转化为可控、可审计的标准流程；通过健康度算子的三态判定、区域级结果和结构化 Issue，将“无法判断”与“确定不合格”分离，兼顾巡检覆盖率与告警准确性。最终沉淀出“权限准备—自动发现—批量治理—持续复检”的工程闭环，并为稳定性看板和 Flinx 自动修复提供标准化输入。

## 七、总结

在这项工作中，我完成了从问题识别、服务盘点、跨区域权限申请、方案设计、工具开发、灰度验证、批量治理到持续巡检的完整闭环。我通过部门服务账号批量申请 24 个核心 PSM 在三个区域的相关权限，并使用服务账号 JWT 驱动脚本完成准入条件配置，推动核心服务完成等级升级和报警能力补齐；同时沉淀了可持续复用的 ByteFaaS 报警治理工具，并落地每日服务等级对齐检查算子，使同类治理从一次性人工项目转变为可交接、可重复、可追踪、可持续发现回退问题的工程流程。
